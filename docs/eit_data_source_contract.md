# Контракт источника данных ЭИТ

## Основание

Контракт получен из фактических JSON и загрузчиков соседних проектов:

- `eit_project_6_air/measurments/sample_sitting.json`: 98 кадров, `param=1_1_100_5.000000`;
- `eit_project_2_calculation/m1.json`: 93 кадра того же аппаратного формата;
- `eit_project_3_measurements_generator/output*.json`: кадры и объект `_metadata` генератора;
- `eit_project_4_monitoring/examples/*.json`: 300 кадров, `_metadata.fps=25`;
- `eit_project_2_calculation/reference_data/v_sim_adjacent_16e_208ch.json`: явные `16` электродов, `208` каналов и протокол `adjacent`.

Во всех файлах измерительный кадр имеет 208 конечных чисел. Это соответствует
смежной схеме `N × (N - 3) = 16 × 13 = 208`. Абсолютная физическая нумерация
электродов, знак, единицы и порядок каналов не подтверждены спецификацией
прибора, поэтому идентификатор профиля —
`adjacent-16x13-hypothesis-v1`.

## Жизненный цикл источника

Qt-независимый `DataSource` предоставляет операции:

1. `discover()` — перечислить доступные устройства;
2. `connect(device_id)` — подключиться с ограниченным временем ожидания;
3. `configure(settings)` — применить проверенные параметры до старта;
4. `start()` — начать выдачу кадров;
5. `read_frame()` — получить следующий нормализованный кадр;
6. `stop()` — безопасно прекратить выдачу;
7. `disconnect()` — освободить транспорт;
8. `reconnect()` — переподключиться без молчаливой смены настроек;
9. `drain_events()` — получить накопленные события состояния и ошибок.

Допустимые состояния: `disconnected → connected → configured → running`.
Ошибка переводит аппаратный адаптер в `failed`; повторный запуск возможен
только после явного переподключения.

## Сырой кадр

`RawMeasurementFrame` содержит:

- `sequence_number`: целое число от `0`, монотонно возрастает на единицу;
- `timestamp_utc`: timezone-aware UTC timestamp;
- `timestamp_source`: `device`, `recording_metadata` или `synthesized`;
- `belt_index`: для MVP только `0`;
- `protocol_id`;
- `channel_values`: ровно 208 конечных чисел;
- `quality`: `valid`, `degraded`, `stale` или `unavailable`;
- `simulated`: обязательная маркировка синтетических данных.

Сырой кадр является границей транспорта и последующей реконструкции.
Существующий `EITFrame` — нормализованный результат адаптера для текущего
read model: sequence/timestamp сохраняются, а глобальная кривая, ROI и карта
являются производными данными. Аппаратный адаптер TASK-16 не должен выдавать
сырые напряжения за реконструированную карту.

Текущая исследовательская реализация преобразования `RawMeasurementFrame` в
`EITFrame`, включая опорный интервал, FEM/CEM, GREIT и ограничения, описана в
[«Реконструкция реальных измерений ЭИТ»](eit_reconstruction.md).

## Файлы JSON, CSV и Excel

JSON, CSV и Excel `.xlsx` можно использовать как источник при запуске с
`EIT_DATA_MODE=fromfile`. Путь задаётся через `EIT_FROMFILE_PATH`, скорость —
через `EIT_FROMFILE_SPEED`; каждый новый сеанс начинает чтение с первого
кадра и циклически продолжает комплектную запись с монотонными sequence/time.
Архивный просмотр и явный импорт файла остаются конечными. Поставляемая запись
из соседнего проекта маркируется
`simulated=true` и не смешивается с данными аппаратного режима.

Принимается корневой JSON-объект:

```json
{
  "0": {"0": [208 чисел]},
  "1": {"0": [208 чисел]},
  "param": "1_1_100_5.000000",
  "_metadata": {"n_electrodes": 16, "n_channels": 208, "fps": 25.0}
}
```

Допускается прямой массив кадра вместо `{"0": [...]}`. Для совместимости
принимается ровно один из объектов `metadata` или `_metadata`.

Обязательные правила:

- ключи кадров — канонические десятичные строки `0..N-1` без пропусков;
- дублированные ключи отклоняются до преобразования JSON в словарь;
- все кадры имеют ровно 208 конечных чисел;
- отрицательные значения допустимы: они присутствуют в проектах 3 и 4;
- `metadata.frame_rate_hz` и legacy `_metadata.fps` имеют приоритет;
- затем FPS оценивается как `frame_count / duration_seconds`;
- иначе используется явно настроенный fallback, помеченный
  `configured_fallback`;
- `metadata.recorded_at` обязан быть ISO 8601 с UTC offset;
- если timestamp отсутствует, импортер строит равномерную ось по FPS и
  маркирует её `synthesized`;
- из legacy `param` третье поле интерпретируется как кГц, четвёртое — как мА;
  это предположение, а не подтверждённая спецификация устройства.

Для CSV и Excel действует построчный контракт:

- одна строка — один кадр, ровно 208 числовых значений без заголовка;
- CSV может использовать `;`, запятую или табуляцию; завершающий разделитель
  без значения допускается;
- в `.xlsx` читается первый лист, включая сохранённые результаты формул;
- пустые строки пропускаются, а строки из 208 нулей не создают кадр;
- после удаления нулевых строк кадры получают последовательные номера от нуля
  и синтезированные UTC timestamps с настроенной fallback-частотой;
- неполные строки, пустые ячейки среди 208 каналов, текст и не конечные числа
  отклоняют весь файл, чтобы не менять порядок каналов молча.

## Таймауты, пропуски и переподключение

Значения по умолчанию `DataSourceTimingPolicy`:

- подключение: 5 с;
- ожидание кадра: 0,2 с;
- данные считаются устаревшими после 0,5 с;
- после трёх последовательных таймаутов источник сообщает ошибку;
- интервалы повторного подключения: 0,25; 1; 2; 5 с, далее 5 с.

Таймаут не создаёт фиктивный кадр. Пропуск определяется по sequence number:
при `expected=15`, `received=18` регистрируются три потерянных кадра и событие
`frame_gap`; кадр 18 можно обработать как `degraded`. Дубликат или уменьшение
sequence number вызывает `DataSourceSequenceError`. После reconnect новая
последовательность начинается только вместе с новой явно обозначенной
сессией/эпохой источника; внутри исследования номера не переиспользуются.

События `state_changed`, `timeout`, `frame_gap` и `error` содержат UTC-время,
текущее состояние, ожидаемый/полученный sequence, число потерь и признак
восстановимости. Они не зависят от Qt и могут транслироваться в общую шину
приложения.

## Не подтверждено и не должно угадываться

- физическая нумерация и ориентация электродов;
- знак и единицы 208 каналов;
- наличие аппаратного timestamp в целевом транспортном протоколе;
- первые два поля `param`;
- контрольная сумма, framing, endianness и команда конфигурации устройства.

Эти сведения должны поступить из спецификации/профиля конкретного прибора в
TASK-16. JSON-контракт не подменяет аппаратный протокол.
